Melange resolves configuration from multiple sources in the following order of precedence (highest wins):

1. **CLI flags**
2. **Environment variables** (`MELANGE_*` prefix)
3. **Config file** (`melange.yaml` or `melange.yml`)
4. **Built-in defaults**

## Config file

Melange automatically discovers a config file by searching the current directory and walking up to the repository root (`.git` boundary, max 25 levels). It checks these names in order:

1. `melange.yaml`
2. `melange.yml`
3. `melange/config.yaml`
4. `melange/config.yml`
5. `melange/melange.yaml`
6. `melange/melange.yml`

The first match wins. To override auto-discovery:

```bash
melange --config /path/to/custom-config.yaml migrate
```

<Info>
The `melange/` directory is the default layout created by `melange init`. Existing `melange.yaml` files at the project root continue to work — both layouts are fully supported.
</Info>

## Scaffolding a config file

Run `melange init` to generate a config file interactively, or create one manually:

```yaml
# melange.yaml

# Path to OpenFGA schema file (used by all commands)
schema: schemas/schema.fga

# Database connection (used by migrate, status, doctor)
database:
  # Option 1: Full connection URL
  url: postgres://user:password@localhost:5432/mydb?sslmode=prefer

  # Option 2: Discrete fields (used when url is empty)
  # host: localhost
  # port: 5432
  # name: mydb
  # user: melange
  # password: secret
  # sslmode: prefer

# Code generation settings
generate:
  client:
    runtime: go
    schema: schemas/schema.fga  # overrides top-level schema
    output: internal/authz
    package: authz
    filter: can_
    id_type: string

  # Migration file generation (for external frameworks)
  migration:
    output: db/migrations
    name: melange
    format: split  # "split" or "single"

# Migration settings
migrate:
  dry_run: false
  force: false

# Doctor command settings
doctor:
  verbose: false
  skip_performance: false
```

## Viewing effective configuration

Use `melange config show` to inspect the merged result:

```bash
# Show effective configuration
melange config show

# Show with config file path
melange config show --source
```

**Example output**

```
Config file: /path/to/project/melange.yaml

schema: schemas/schema.fga
database:
  url: postgres://localhost/mydb
  host: ""
  port: 5432
  ...
```

## Configuration reference

### Top-level settings

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `schema` | string | `schemas/schema.fga` | Path to the OpenFGA schema file |

### `database`

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `url` | string | — | Full PostgreSQL connection URL |
| `host` | string | — | Host (used when `url` is empty) |
| `port` | int | `5432` | Port |
| `name` | string | — | Database name |
| `user` | string | — | Database user |
| `password` | string | — | Database password |
| `sslmode` | string | `prefer` | SSL mode |

**Connection URL format**

```
postgres://user:password@host:5432/dbname?sslmode=require
```

When using discrete fields, `host`, `name`, and `user` are required.

**SSL mode values**

| Value | Description |
|-------|-------------|
| `disable` | No SSL |
| `allow` | Try non-SSL first, then SSL |
| `prefer` | Try SSL first, then non-SSL (default) |
| `require` | Require SSL |
| `verify-ca` | Require SSL and verify CA |
| `verify-full` | Require SSL, verify CA and hostname |

### `generate.client`

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `runtime` | string | — | Target runtime: `go`, `typescript` |
| `schema` | string | (top-level `schema`) | Path to schema file |
| `output` | string | — | Output directory for generated code |
| `package` | string | `authz` | Package/module name |
| `filter` | string | — | Relation prefix filter (e.g., `can_`) |
| `id_type` | string | `string` | ID type for constructors |

### `generate.migration`

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `output` | string | `""` (stdout) | Output directory for migration files |
| `name` | string | `melange` | Migration name suffix in filenames |
| `format` | string | `split` | Output format: `split` or `single` |

<Warning>
Do not configure `generate.migration.output` and run `melange migrate` against the same database. The two strategies track state differently and mixing them can produce warnings.
</Warning>

### `migrate`

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `dry_run` | bool | `false` | Output SQL without applying |
| `force` | bool | `false` | Force migration even if schema is unchanged |

### `doctor`

| Key | Type | Default | Description |
|-----|------|---------|-------------|
| `verbose` | bool | `false` | Show detailed output |
| `skip_performance` | bool | `false` | Skip performance checks (view analysis) |

## Environment variables

All config options are available as environment variables using the `MELANGE_` prefix with nested keys separated by underscores.

| Environment variable | Config path |
|---------------------|-------------|
| `MELANGE_SCHEMA` | `schema` |
| `MELANGE_DATABASE_URL` | `database.url` |
| `MELANGE_DATABASE_HOST` | `database.host` |
| `MELANGE_DATABASE_PORT` | `database.port` |
| `MELANGE_DATABASE_NAME` | `database.name` |
| `MELANGE_DATABASE_USER` | `database.user` |
| `MELANGE_DATABASE_PASSWORD` | `database.password` |
| `MELANGE_DATABASE_SSLMODE` | `database.sslmode` |
| `MELANGE_GENERATE_CLIENT_RUNTIME` | `generate.client.runtime` |
| `MELANGE_GENERATE_CLIENT_SCHEMA` | `generate.client.schema` |
| `MELANGE_GENERATE_CLIENT_OUTPUT` | `generate.client.output` |
| `MELANGE_GENERATE_CLIENT_PACKAGE` | `generate.client.package` |
| `MELANGE_GENERATE_CLIENT_FILTER` | `generate.client.filter` |
| `MELANGE_GENERATE_CLIENT_ID_TYPE` | `generate.client.id_type` |
| `MELANGE_GENERATE_MIGRATION_OUTPUT` | `generate.migration.output` |
| `MELANGE_GENERATE_MIGRATION_NAME` | `generate.migration.name` |
| `MELANGE_GENERATE_MIGRATION_FORMAT` | `generate.migration.format` |
| `MELANGE_MIGRATE_DRY_RUN` | `migrate.dry_run` |
| `MELANGE_MIGRATE_FORCE` | `migrate.force` |
| `MELANGE_DOCTOR_VERBOSE` | `doctor.verbose` |
| `MELANGE_DOCTOR_SKIP_PERFORMANCE` | `doctor.skip_performance` |

Boolean environment variables accept `true`/`false` or `1`/`0`.

## Configuration inheritance

Per-command settings override the top-level defaults:

```yaml
# Top-level default
schema: schemas/schema.fga

generate:
  client:
    # Overrides top-level schema for generate only
    schema: schemas/api-schema.fga
```

## Example configurations

<AccordionGroup>
  <Accordion title="Local development">

    ```yaml
    schema: schemas/schema.fga

    database:
      url: postgres://localhost/myapp_dev

    generate:
      client:
        runtime: go
        output: internal/authz
        package: authz
    ```

  </Accordion>

  <Accordion title="CI/CD pipeline">

    Inject the database URL from your secrets manager and keep everything else in the config file:

    ```yaml
    # melange.yaml (committed)
    schema: schemas/schema.fga

    generate:
      client:
        runtime: go
        output: internal/authz
    ```

    ```yaml
    # .github/workflows/deploy.yml
    env:
      MELANGE_DATABASE_URL: ${{ secrets.DATABASE_URL }}
    ```

  </Accordion>

  <Accordion title="Multi-environment">

    Use separate config files per environment:

    ```bash
    melange --config melange.dev.yaml migrate
    melange --config melange.prod.yaml migrate
    ```

    Or share a base config and override the database URL per environment:

    ```bash
    MELANGE_DATABASE_URL="postgres://prod-host/myapp" melange migrate
    ```

  </Accordion>
</AccordionGroup>

## Security considerations

- Prefer environment variables for secrets in production
- Avoid committing `melange.yaml` files that contain `database.password` to version control
- Use connection URLs with credentials stored in a secrets manager
- For local development, discrete fields in a `.gitignore`-d config file are acceptable
