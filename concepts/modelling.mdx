Melange uses the [OpenFGA](https://openfga.dev) DSL to define authorization models. You write a `.fga` file describing your object types and the relations between them; Melange compiles that file into PostgreSQL functions.

<Info>
This page covers the DSL constructs that Melange supports. For in-depth modelling patterns and design guidance, see the [OpenFGA modelling documentation](https://openfga.dev/docs/modeling).
</Info>

## Schema structure

Every `.fga` file starts with a model header, followed by one or more type definitions:

```fga
model
  schema 1.1

type user

type organization
  relations
    define owner: [user]
    define admin: [user] or owner
    define member: [user] or admin
```

| Element | Description |
|---------|-------------|
| `model` | Required header — marks the start of the schema |
| `schema 1.1` | Schema version — Melange supports OpenFGA Schema 1.1 |
| `type` | Declares an object type (`user`, `repository`, `team`, etc.) |
| `relations` | Block of relation definitions for a type |
| `define` | Defines one relation and the rules for granting it |

## Types

Types represent the entities in your system. You declare them with `type <name>`:

```fga
type user
type organization
type repository
type team
```

A type with no `relations` block (like `user`) acts as a **subject type** — the "who" in permission checks. Types with relations define resources that can be accessed.

## Relations

Relations define how subjects connect to objects. Every relation is a `define` statement inside a `relations` block.

### Direct assignment

Allow specific subject types to be assigned directly:

```fga
type document
  relations
    define owner: [user]
    define editor: [user, team]
```

- `[user]` — only `user` subjects can be directly assigned this relation.
- `[user, team]` — either `user` or `team` subjects can be assigned.

In your `melange_tuples` view, a row with `relation = 'owner'` grants the `owner` relation to the subject.

### Role hierarchies (`or`)

The `or` keyword creates a union — the relation is granted if **any** of the conditions match:

```fga
type organization
  relations
    define owner: [user]
    define admin: [user] or owner    -- admins, plus everyone who is an owner
    define member: [user] or admin   -- members, plus all admins (and owners)
```

Melange resolves these hierarchies at compile time. Checking `admin` automatically covers all `owner` relations without runtime recursion.

### Parent inheritance (`from`)

The `from` keyword creates a **tuple-to-userset** relationship — inherit a relation from a linked parent object:

```fga
type repository
  relations
    define org: [organization]           -- link to parent organization
    define can_read: can_read from org   -- inherit can_read from the org
    define can_write: can_write from org
```

When checking `can_read` on a repository, Melange:
1. Looks up the `org` relation to find the linked organization.
2. Checks `can_read` on that organization.

<Tip>
Keep inheritance shallow. Each `from` hop adds a join to the generated function. One level of inheritance is ideal; more than two should be avoided.
</Tip>

### Intersection (`and`)

The `and` keyword requires **all** conditions to match:

```fga
type project
  relations
    define can_deploy: writer and approved
```

A user needs both `writer` and `approved` on the same project to have `can_deploy`.

### Exclusion (`but not`)

The `but not` keyword denies the relation when a condition is true:

```fga
type pull_request
  relations
    define repo:       [repository]
    define author:     [user]
    define can_review: can_read from repo but not author
```

A user can review a pull request if they have `can_read` on the repository **and** are not the author.

<Warning>
Exclusion patterns are slower than positive checks because they require an additional lookup to evaluate the excluded condition. Use them only when necessary.
</Warning>

### Wildcards (`[user:*]`)

The wildcard syntax `[type:*]` represents all subjects of a given type — useful for public access:

```fga
type repository
  relations
    define public:   [user:*]
    define can_read: public or member
```

In your `melange_tuples` view, map public resources using `'*'` as the `subject_id`:

```sql
SELECT
    'user'       AS subject_type,
    '*'          AS subject_id,   -- wildcard: matches any user
    'public'     AS relation,
    'repository' AS object_type,
    id::text     AS object_id
FROM repositories
WHERE is_public = true
```

The `check_permission` function automatically checks for both the specific subject and `'*'`.

### Userset references (`[type#relation]`)

You can grant a relation to all members of a group using the `[type#relation]` syntax:

```fga
type team
  relations
    define member: [user]

type organization
  relations
    define admin: [user, team#member] or owner
```

`[team#member]` means "users who hold the `member` relation on any `team` object". The tuple in `melange_tuples` uses `subject_type = 'team'` and a non-empty `subject_relation`.

## Complete examples

<AccordionGroup>
  <Accordion title="Organization with teams" defaultOpen={false}>

```fga
model
  schema 1.1

type user

type team
  relations
    define member: [user]

type organization
  relations
    define owner:  [user]
    define admin:  [user, team#member] or owner
    define member: [user, team#member] or admin

type repository
  relations
    define org:        [organization]
    define can_read:   member from org
    define can_write:  admin from org
    define can_delete: owner from org
```

  </Accordion>
  <Accordion title="Document sharing" defaultOpen={false}>

```fga
model
  schema 1.1

type user

type folder
  relations
    define owner:  [user]
    define viewer: [user] or owner

type document
  relations
    define parent: [folder]
    define owner:  [user]
    define editor: [user] or owner
    define viewer: [user] or editor or viewer from parent
```

Documents inherit viewer access from their parent folder.

  </Accordion>
  <Accordion title="Multi-tenant SaaS" defaultOpen={false}>

```fga
model
  schema 1.1

type user

type tenant
  relations
    define admin:  [user]
    define member: [user] or admin

type project
  relations
    define tenant:    [tenant]
    define owner:     [user]
    define member:    [user] or owner or member from tenant
    define can_read:  member
    define can_write: owner or admin from tenant
```

  </Accordion>

## Best practices

<AccordionGroup>
  <Accordion title="Separate roles from permissions">

Define roles that are assigned directly, then derive named permissions from those roles:

```fga
type repository
  relations
    # Roles (assigned directly via tuples)
    define owner:  [user]
    define admin:  [user] or owner
    define writer: [user] or admin
    define reader: [user] or writer

    # Permissions (derived — never assigned directly)
    define can_read:   reader
    define can_write:  writer
    define can_delete: owner
```

This pattern makes it clear which relations appear in tuples and which are inferred.

  </Accordion>
  <Accordion title="Use consistent naming">

**Roles**: `owner`, `admin`, `member`, `viewer`

**Permissions**: `can_read`, `can_write`, `can_delete`, `can_invite`

**Parent links**: `org`, `parent`, `folder`, `repo`

  </Accordion>
  <Accordion title="Avoid deep inheritance chains">

Each `from` hop adds a join to the generated SQL. Keep inheritance to one level where possible:

```fga
# Good: one hop
define can_read: can_read from org

# Avoid: chained hops add complexity
define can_read: can_read from parent from grandparent
```

  </Accordion>
</AccordionGroup>

## Validating your schema

Check syntax before running a migration:

```bash
melange validate --schema schemas/schema.fga
```

For deeper semantic validation, use the OpenFGA CLI:

```bash
# Install
go install github.com/openfga/cli/cmd/fga@latest

# Validate
fga model validate --file schemas/schema.fga
```
