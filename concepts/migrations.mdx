---
title: "Running migrations"
description: "Apply your compiled schema to PostgreSQL using built-in or external migration tools."
---

Melange compiles your `.fga` schema into SQL functions that must be installed in PostgreSQL before permission checks can run. There are two ways to get those functions into your database.

## Two migration strategies

| | Built-in (`melange migrate`) | External (`melange generate migration`) |
|---|---|---|
| **How it works** | Connects to PostgreSQL and applies SQL directly | Produces versioned `.sql` files you apply yourself |
| **Best for** | Solo projects, rapid prototyping, simple deployments | Teams using golang-migrate, Atlas, Flyway, etc. |
| **Change tracking** | `melange_migrations` table in the database | Your framework's own tracking |
| **Database access required** | Yes — at migration time | Only when using `--db` comparison mode |
| **CI review** | Via `--dry-run` | Natively — SQL files are committed and reviewed in PRs |

<Warning>
Pick one strategy per database. Mixing both is discouraged — `melange migrate` will warn if it detects that `generate migration` has been used, and vice versa.
</Warning>

## Built-in migrations

Point `melange migrate` at your database and schema file:

```bash
melange migrate \
  --db postgres://localhost/mydb \
  --schema schemas/schema.fga
```

Melange connects, generates the SQL functions, and applies them in a single transaction. It records each migration in a `melange_migrations` table so it can skip unchanged schemas and clean up orphaned functions automatically.

### When to use

- You control the database directly (local dev, small teams).
- You don't need SQL migrations checked into version control.
- You want the simplest possible workflow.

### Key behaviors

<AccordionGroup>
  <Accordion title="Skip-if-unchanged">

Melange checksums your schema and skips the migration when nothing has changed. Use `--force` to override:

```bash
melange migrate --db postgres://localhost/mydb --schema schemas/schema.fga --force
```

  </Accordion>
  <Accordion title="Dry run">

Preview the SQL that would be applied without touching the database:

```bash
melange migrate --db postgres://localhost/mydb --schema schemas/schema.fga --dry-run
```

  </Accordion>
  <Accordion title="Orphan cleanup">

When you remove a relation from your schema, Melange automatically drops the corresponding functions from the database on the next `melange migrate` run. You don't need to write `DROP FUNCTION` statements manually.

  </Accordion>
</AccordionGroup>

## External migration frameworks

If your team uses a migration framework, `melange generate migration` produces versioned SQL files that slot into your existing workflow:

```bash
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations
```

This writes timestamped migration files (e.g., `20260322143000_melange.up.sql` / `.down.sql`) containing the same SQL that `melange migrate` would apply, but as static files you commit, review, and apply through your framework.

### When to use

- Your team uses golang-migrate, Atlas, Flyway, Liquibase, or a similar tool.
- You want migration SQL reviewed in pull requests before it reaches production.
- You need to coordinate Melange schema changes with other database migrations.
- You don't want Melange to have direct database access in CI.

### Output formats

<Tabs>
  <Tab title="Split (default)">

Produces separate up and down files:

```
db/migrations/20260322143000_melange.up.sql
db/migrations/20260322143000_melange.down.sql
```

```bash
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations \
  --format split
```

  </Tab>
  <Tab title="Single">

Produces one file containing both UP and DOWN sections:

```
db/migrations/20260322143000_melange.sql
```

```bash
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations \
  --format single
```

  </Tab>
  <Tab title="Stdout">

Write directly to stdout for scripting:

```bash
# UP migration to stdout
melange generate migration --schema schemas/schema.fga --up

# DOWN migration to stdout
melange generate migration --schema schemas/schema.fga --down
```

  </Tab>
</Tabs>

## Comparison modes

By default, `generate migration` emits every function — a full migration. This is correct for the first migration, but for subsequent changes you usually only want the functions that changed. Melange supports three comparison modes.

### Full mode (default)

No comparison flag. The UP migration includes all functions. Use this for your first migration or whenever you want a complete snapshot:

```bash
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations
```

### Database comparison (`--db`)

Reads the most recent `melange_migrations` record to determine what existed before. The UP migration includes only changed, new, or orphaned functions:

```bash
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations \
  --db postgres://localhost/mydb
```

This is the most precise mode, but requires database access at generation time.

### Git comparison (`--git-ref`)

Compiles the schema from a git ref and compares the result against the current schema. No database access required — ideal for CI pipelines:

```bash
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations \
  --git-ref main
```

Common patterns:

```bash
--git-ref main      # compare against the main branch
--git-ref HEAD~1    # compare against the previous commit
--git-ref v1.2.0    # compare against a release tag
```

### File comparison (`--previous-schema`)

Compiles a previous schema from a local file and compares:

```bash
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations \
  --previous-schema schemas/schema.fga.bak
```

Useful when you keep a copy of the last-deployed schema alongside your current one.

<Info>
The three comparison flags (`--db`, `--git-ref`, `--previous-schema`) are mutually exclusive. Specify at most one.
</Info>

## How change detection works

When a comparison mode is active, Melange computes a SHA-256 checksum of each function's SQL body — for both the current and previous state. Only functions with a changed or missing checksum appear in the UP migration.

Dispatcher functions (`check_permission`, `check_permission_internal`, `list_accessible_objects`, etc.) are **always regenerated** because they contain a `CASE` branch for every relation and must be updated whenever any relation changes.

Functions that existed before but are absent from the current schema are treated as **orphans** and receive `DROP FUNCTION IF EXISTS` statements in the UP migration.

## What the generated files look like

<Accordion title="UP migration example" defaultOpen={false}>

For a schema with a single `document.viewer` relation:

```sql
-- Melange Migration (UP)
-- Melange version: v0.7.3
-- Schema checksum: 9f3a...
-- Codegen version: 1

-- ============================================================
-- Check Functions (1 functions)
-- ============================================================

CREATE OR REPLACE FUNCTION check_document_viewer(
    p_subject_type TEXT,
    p_subject_id   TEXT,
    p_object_id    TEXT,
    p_visited      TEXT[] DEFAULT ARRAY[]::TEXT[]
) RETURNS INTEGER AS $$
BEGIN
    IF EXISTS (
        SELECT 1
        FROM melange_tuples
        WHERE object_type = 'document'
          AND relation    IN ('viewer')
          AND object_id   = p_object_id
          AND subject_type = p_subject_type
          AND subject_id   = p_subject_id
        LIMIT 1
    ) THEN
        RETURN 1;
    ELSE
        RETURN 0;
    END IF;
END;
$$ LANGUAGE plpgsql STABLE;

-- ============================================================
-- Check Dispatchers
-- ============================================================

CREATE OR REPLACE FUNCTION check_permission_internal(
    p_subject_type TEXT,
    p_subject_id   TEXT,
    p_relation     TEXT,
    p_object_type  TEXT,
    p_object_id    TEXT,
    p_visited      TEXT[] DEFAULT ARRAY[]::TEXT[]
) RETURNS INTEGER AS $$
BEGIN
    IF array_length(p_visited, 1) >= 25 THEN
        RAISE EXCEPTION 'resolution too complex' USING ERRCODE = 'M2002';
    END IF;
    RETURN (SELECT CASE
        WHEN (p_object_type = 'document' AND p_relation = 'viewer')
            THEN check_document_viewer(p_subject_type, p_subject_id, p_object_id, p_visited)
        ELSE 0
    END);
END;
$$ LANGUAGE plpgsql STABLE;

CREATE OR REPLACE FUNCTION check_permission(
    p_subject_type TEXT,
    p_subject_id   TEXT,
    p_relation     TEXT,
    p_object_type  TEXT,
    p_object_id    TEXT
) RETURNS INTEGER AS $$
    SELECT check_permission_internal(
        p_subject_type, p_subject_id, p_relation,
        p_object_type, p_object_id, ARRAY[]::TEXT[]);
$$ LANGUAGE sql STABLE;
```

</Accordion>

<Accordion title="DOWN migration example" defaultOpen={false}>

```sql
-- Melange Migration (DOWN)
-- To restore a previous version, apply that version's UP migration.

DROP FUNCTION IF EXISTS check_document_viewer CASCADE;
DROP FUNCTION IF EXISTS check_document_viewer_no_wildcard CASCADE;
DROP FUNCTION IF EXISTS list_document_viewer_objects CASCADE;
DROP FUNCTION IF EXISTS list_document_viewer_subjects CASCADE;

DROP FUNCTION IF EXISTS check_permission CASCADE;
DROP FUNCTION IF EXISTS check_permission_internal CASCADE;
DROP FUNCTION IF EXISTS check_permission_no_wildcard CASCADE;
DROP FUNCTION IF EXISTS check_permission_no_wildcard_internal CASCADE;
DROP FUNCTION IF EXISTS check_permission_bulk CASCADE;
DROP FUNCTION IF EXISTS list_accessible_objects CASCADE;
DROP FUNCTION IF EXISTS list_accessible_subjects CASCADE;
```

</Accordion>

<Accordion title="Incremental migration example (--git-ref)" defaultOpen={false}>

When you add an `editor` relation to `document`, only the changed functions appear:

```sql
-- Melange Migration (UP)
-- Melange version: v0.7.3
-- Schema checksum: b7e4...
-- Previous state: git:main
-- Changed functions: 2 of 4

CREATE OR REPLACE FUNCTION check_document_editor(
    -- new function for the added relation
) RETURNS INTEGER AS $$ /* ... */ $$ LANGUAGE plpgsql STABLE;

CREATE OR REPLACE FUNCTION check_document_editor_no_wildcard(
    -- no-wildcard variant
) RETURNS INTEGER AS $$ /* ... */ $$ LANGUAGE plpgsql STABLE;

-- Dispatchers are always regenerated to include the new CASE branch
CREATE OR REPLACE FUNCTION check_permission_internal( /* ... */ )
RETURNS INTEGER AS $$
BEGIN
    RETURN (SELECT CASE
        WHEN (p_object_type = 'document' AND p_relation = 'editor')
            THEN check_document_editor(...)
        WHEN (p_object_type = 'document' AND p_relation = 'viewer')
            THEN check_document_viewer(...)
        ELSE 0
    END);
END;
$$ LANGUAGE plpgsql STABLE;
```

If you remove a relation, the comparison mode also emits `DROP` statements for the orphaned functions:

```sql
-- Drop removed functions
DROP FUNCTION IF EXISTS check_document_editor CASCADE;
DROP FUNCTION IF EXISTS check_document_editor_no_wildcard CASCADE;
```

</Accordion>

## CI/CD workflows

<Tabs>
  <Tab title="golang-migrate">

**First-time setup:**

```bash
# Generate the initial full migration
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations \
  --name melange

# Apply with golang-migrate
migrate -path db/migrations -database "$DATABASE_URL" up
```

**Schema change in a PR:**

```bash
# Edit schemas/schema.fga, then generate a diff migration
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations \
  --git-ref main

# Commit both the schema change and the generated SQL
git add schemas/schema.fga db/migrations/
git commit -m "Add editor relation to document type"
```

  </Tab>
  <Tab title="Atlas">

```bash
# Generate migration SQL
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations \
  --git-ref main

# Apply with Atlas
atlas migrate apply --dir file://db/migrations --url "$DATABASE_URL"
```

  </Tab>
  <Tab title="Flyway">

```bash
# Generate migration SQL
melange generate migration \
  --schema schemas/schema.fga \
  --output db/migrations \
  --git-ref main

# Apply with Flyway
flyway migrate -url="$JDBC_URL" -locations="filesystem:db/migrations"
```

  </Tab>
  <Tab title="CI validation">

```bash
# Validate schema syntax
melange validate --schema schemas/schema.fga

# Check there is no uncommitted migration drift
# (generate to stdout and verify manually or diff against committed files)
melange generate migration \
  --schema schemas/schema.fga \
  --git-ref main \
  --up
```

  </Tab>
</Tabs>
